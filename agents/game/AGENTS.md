# 独立游戏项目开发原则（AGENTS.md）

本文件用于独立游戏项目，作为通用项目开发原则的补充，不替代通用原则。

开始游戏项目工作时同时读取：

https://github.com/gongfpp/aki-agent-kit/blob/main/agents/project/AGENTS.md?raw=1

## 玩家路径优先于代码形态

- 修改前先理解当前真实玩家流程：启动、菜单、进入游戏、核心循环、失败/成功、结算、下一轮。
- 判断一个系统价值时，先问玩家是否能真实触发、感知和理解，再讨论代码是否优雅。
- 核心循环、操作反馈、失败/成功反馈和重新开始路径优先于外围系统。
- 设计取舍以玩家体验和项目继续开发的成本为核心，不以“架构更高级”为目标。

## 优先完成可玩的垂直切片

- 新玩法先做最小可玩闭环，验证输入、反馈、状态变化、失败/成功和结算，再扩大内容量。
- 在核心玩法尚未稳定前，不提前建设多人、Mod、DLC、大世界、大规模角色系统等推测性能力。
- 系统规模服务于当前项目真实规模；只有已经出现重复和变化压力时再抽象。

## 游戏状态必须有明确 Owner

- Player、UI、GameManager、关卡、存档不得同时维护同一事实的独立副本。
- UI 应观察权威游戏状态，而不是自己成为第二个状态管理器。
- 存档负责持久化和恢复权威状态，不应成为运行时真相来源。
- 战斗、场景切换、Loading、AI、任务等复杂流程必须明确状态 Owner、修改者和观察者。

## 场景、资源与生命周期

- Scene / Prefab / Resource / Asset / Signal / Event / Timer / Coroutine / async task 的创建、连接和释放必须有明确生命周期。
- 删除脚本或功能前同时检查场景序列化引用、动画轨道、资源引用、Input Map、Localization、Audio、Save Field 和编辑器配置。
- 不因为代码搜索不到引用就直接删除资源；引擎序列化数据和编辑器配置同样可能建立依赖。
- 临时 Debug、Prototype、Benchmark、Cheat 和测试场景应有明确用途；失去用途后及时清理。

## 优先使用引擎已有能力

- Tween、资源加载、序列化、输入、场景生命周期、动画、导航等能力优先使用引擎成熟实现。
- 自建基础设施必须有真实约束作为理由，而不是为了统一风格或未来可能换引擎。
- 插件只有在减少总维护成本时才值得引入；大量 Adapter、Override 和兼容层会抵消插件价值。

## 内容成本也是架构成本

- 评估玩法时同时计算代码成本和长期内容生产成本。
- 任何需要持续制作大量专属关卡、对话、立绘、动画、音频、数值或事件的系统，都必须证明玩家价值足以覆盖内容成本。
- 已经实现但需要巨大内容量才能不显得半成品的系统，应允许降级、合并或删除。
- 优先复用内容生产管线和数据结构，不为单个小功能建立独立内容工作流。

## 交互、反馈与可读性

- 玩家操作必须有及时、可辨认的视觉、声音或状态反馈；重要结果不能只藏在日志或数值里。
- UI 状态与游戏状态保持一致，避免按钮可点但行为无效、界面已更新但游戏状态未更新等分裂状态。
- 输入、暂停、返回、失败重开、存档读取等基础流程需要符合平台直觉，并保持路径可恢复。
- 美术表现服务于信息层级和玩法理解；不要因为视觉效果牺牲可读性和反馈速度。

## 存档与兼容

- 明确哪些数据属于运行时状态，哪些属于持久化数据。
- 修改 Save Schema、资源 ID、场景路径或关键枚举时先判断旧存档兼容风险。
- 如果项目尚未承诺长期存档兼容，可以选择更简单的迁移策略，但必须明确这个决策。

## 性能

- 优先处理玩家真实可感知的卡顿、加载、掉帧和内存问题，不做没有数据支持的微优化。
- 优化前确认瓶颈来自 CPU、GPU、IO、脚本、资源加载还是内容规模。
- 对象池、缓存、预加载、异步加载等机制只有在真实性能问题出现时才引入，并明确其失效和清理路径。

## 测试与试玩

- 代码测试不能替代实际试玩。核心玩法改动至少验证一遍真实玩家路径。
- 自动化测试优先覆盖确定性逻辑、存档、数据转换、经济/数值规则和容易回归的状态转换。
- 视觉、手感、节奏和可理解性主要通过运行游戏、录屏、截图和实际交互验证。
- 修复问题时优先复现原问题，再验证修复后玩家路径没有新增阻断。
