# 通用项目开发原则（AGENTS.md）

本文件用于普通软件、App、后端、前端、CLI、工具链等项目。它定义默认开发行为；项目自身已有的架构文档、契约、脚本和项目级约束优先于这里的通用建议。

## 先确认事实，再修改

- 开始工作时先确认仓库结构、构建入口、测试入口、现有文档和与任务直接相关的实现。
- 项目事实以代码、配置、测试、脚本、接口契约和项目级文档为准，不根据目录名或经验猜测不存在的行为。
- 修改前找到真实调用路径、状态 Owner 和外部契约；不要因为代码“看起来不漂亮”就重构。
- 用户要求开始开发或修复时，应持续推进到可审查、可验证的结果；能从仓库确认的信息不要反复询问用户。

## 改动应围绕当前目标

- 优先做能够直接解决当前需求的最小完整改动，避免顺手重构无关模块。
- 新行为优先复用已有扩展点、数据模型和生命周期；只有现有结构确实阻碍需求时才引入新抽象。
- 不为尚未发生的需求提前建设通用框架。抽象应来自已经发生的变化，而不是想象中的未来变化。
- 发现用户提出的实现方式不适合目标时，直接说明原因，并采用更符合目标的方案。

## 状态、资源与生命周期

- 一个事实尽量只有一个权威状态来源；缓存、UI、持久化层和派生状态不得各自演化成第二套真相。
- 对资源、订阅、监听、线程、任务、Timer、连接、锁和临时文件明确 Owner：谁创建，谁释放，何时结束。
- 复杂异步逻辑优先用明确的 transaction / lifecycle / state model 表达，不用一组含义重叠的 bool、sentinel、promise 和 cancellation flag 拼状态。
- 注册行为如果产生副作用，必须绑定对应的清理机制。

## API、模块与能力边界

- 模块边界服务于真实职责和真实变化频率，不为“看起来解耦”增加无消费者的 Interface、Manager、Factory、Registry 或 Wrapper。
- 公共 API、配置、事件和序列化字段一旦成为外部契约，修改时明确兼容范围、迁移方式和失败行为。
- 一个 capability 应覆盖必要的 Definition / Provider / Consumer；只有职责确实独立演进时才拆分。
- 删除能力时同步删除相关测试、文档、配置、生成物和兼容逻辑，不留下半套失效路径。

## 依赖与基础设施

- 标准库或成熟依赖能真正减少自维护实现、测试、文档和风险时优先使用。
- 引入依赖的判断标准是净复杂度是否下降，而不是代码行数是否下降。
- 不用 Wrapper 把原有复杂度搬到另一个目录；如果 glue code、兼容逻辑和升级成本接近被替换实现，通常不值得替换。
- 不手写已有稳定方案覆盖的 parser、retry、glob、diff、序列化等基础能力，除非项目存在明确特殊约束。

## 错误、配置与可观测性

- 失败应可定位：保留必要的错误上下文，不吞异常，不用成功返回掩盖失败。
- 配置、凭据和环境差异应显式；敏感信息不得写入仓库。
- 对关键后台任务、外部调用和状态转换保留足够日志或诊断信息，但不要为了日志本身引入新的状态系统。

## 测试与验证

- 测试与改动风险相称。优先验证真实行为路径、边界条件和最容易回归的契约。
- 不为可逆、影响小、只是复述实现的改动机械增加测试。
- 先运行与改动直接相关的检查；这些通过后，只有出现新改动、新失败或未解决疑点时才扩大验证范围。
- 能运行项目时，至少验证最小成功路径；不能运行时，明确说明缺少的环境或依赖，不伪造验证结果。

## 文档与生成物

- README、API 文档、配置示例和注释应与实际行为同步；对外契约变化必须更新对应说明。
- 生成文件优先由生成器更新，不直接手改；确需直接修改时先确认生成流程不会覆盖改动。
- 临时脚本、调试输出和一次性中间文件在任务结束前清理。

## Git 版本管理

仓库修改任务必须遵循中央 Git 原则：

https://github.com/gongfpp/aki-skills/blob/main/principles/git-version-control.md?raw=1

在开始需要产生 Git 改动的任务时读取最新版本；不要把当前文件中的摘要当作中央规则的替代品。

## 精简审计（按需加载）

只有在用户要求代码审计、精简、清理、架构收敛、删除无用复杂度等任务时，再加载：
