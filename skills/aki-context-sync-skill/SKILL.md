# aki-context-sync-skill

## 目标

把开发过程中只存在于当前会话里的有效上下文沉淀成项目当前状态的一部分，避免重要决策、隐含约束和非显然事实随着会话结束而丢失。

本 Skill 不是会话摘要、开发日志或聊天记录归档。它只持久化未来工作仍需要知道、且当前项目文档尚未准确表达的信息。

## 信息来源

执行时综合检查：

- 当前会话中已经确认的需求、决策、约束和修正后的最终结论；
- 当前任务产生的代码、配置、测试和 Git diff；
- 项目已有 `AGENTS.md`、README、设计文档、架构文档、接口契约、GDD 或其他事实源；
- 与候选事实直接相关的真实实现和调用路径。

会话只能提供候选信息。能够从项目本身验证的内容应以项目事实为准，不把对话中的推测直接升级为长期事实。

## 持久化门槛

一个候选上下文只有同时满足以下条件才值得写入：

- **长期有效**：在当前会话结束后仍可能影响未来开发；
- **不易重建**：未来 Agent 不能通过简单读取代码、配置或已有文档廉价恢复；
- **影响决策**：知道与不知道它，会导致未来实现、审查或维护方式不同；
- **当前有效**：表达的是已经确认的最终状态，而不是讨论过程、临时方案或已经被推翻的中间状态。

不能通过这些条件的候选直接丢弃，不为了“完整记录”落盘。

## 内容洁癖

持久化的是最终事实，不是纠错历史。

- 用户否决过的方案、Agent 犯过的错误、已经解决的误解和临时绕路不自动形成长期负面规则。
- 如果最终目标或当前实现已经完整表达正确状态，不再额外写一条“不要使用旧方案”的说明。
- 能直接从代码、类型、配置、测试或目录结构稳定推导的信息，通常不重复写入上下文文档。
- 已有权威文档已经准确表达的内容不复制到第二处。
- 已经过时、被新决策替代或与当前实现冲突的旧描述应更新或删除，而不是在后面继续追加新说明。
- 推测性的未来可能性、没有形成约束的讨论和一次性执行细节不持久化。

对每一句准备写入的内容执行删除测试：如果删掉它不会提高未来 Agent 做错事、误判架构或破坏契约的概率，就不要写入。

## 选择权威文档

先寻找项目现有的事实源，再决定写到哪里：

- Agent 工作方式、项目级长期执行约束进入项目 `AGENTS.md`；
- 架构与模块职责进入已有架构文档；
- 产品、玩法和交互决策进入已有产品设计或游戏设计文档；
- 接口、数据或部署契约进入对应专项文档；
- README 只保留面向仓库使用者真正需要的信息。

不要因为调用了本 Skill 就创建新的记忆文件。

只有没有任何合适的现有事实源、而候选内容又确实需要长期保存时，才创建 `docs/project-context.md`。该文件只承载跨主题但长期有效、无法合理归属到其他文档的项目上下文，并保持最小结构；没有内容的章节不创建。

## 合并规则

- 修改前完整读取目标文档，先识别语义等价、冲突和已经失效的内容。
- 已有等价事实时不追加；需要更准确时直接更新原位置。
- 同一事实存在多个副本时优先保留最权威的位置，并删除本次有把握收敛的冗余副本。
- 新内容按照现有文档结构融入，不为了标记“由本 Skill 添加”制造永久专区。
- 不重写与本次同步无关的措辞、格式或章节顺序。
- 无法判断哪个事实仍有效时，不自行选择；保留原文并明确报告冲突。

## AGENTS.md 边界

`AGENTS.md` 只保存会影响 Agent 工作方式的长期约束，不作为项目百科或会话记忆库。

如果项目使用 `aki-project-bootstrap-skill`，不得修改 `<!-- aki-agent-kit:bootstrap:start -->` 与 `<!-- aki-agent-kit:bootstrap:end -->` 之间的内容；该 region 只由 bootstrap Skill 管理。需要沉淀的项目特有规则写到 region 外的合适位置。

## 幂等与收敛

本 Skill 必须以收敛当前状态为目标，而不是追加历史：

1. 提取候选上下文；
2. 与项目事实和已有文档核验；
3. 丢弃无长期价值、可廉价重建、重复、过时和过程性信息；
4. 把剩余信息合并进现有权威位置；
5. 再次审计修改后的文档，删除因本次合并产生的重复、否定式残留和无行为价值内容；
6. 在相同会话结论和项目状态下再次执行，结果必须保持不变。

能使用 Git 时，第二次执行以零 diff 作为硬性验收。不要通过时间戳、同步日志、运行次数或自动生成摘要制造每次都变化的文件。

## 与历史记录的关系

项目文档描述当前有效状态。已经被替换的事实由 Git 历史追溯，不为了保存演进过程留在当前事实文档中。

只有项目本身明确维护 CHANGELOG、ADR 或决策历史，并且本次变化符合其记录门槛时，才同步更新对应历史文件；不要把每次 context sync 本身记成事件。

## 输出

完成后简要说明：

- 修改了哪些权威文档；
- 新增、更新或删除了哪些类别的项目事实；
- 是否存在无法确认的冲突；
- 幂等检查是否通过。

被丢弃的候选无需写入项目文件；只有用户需要审查时才在回复中说明主要舍弃理由。
