# aki-game-audit

## 目标

从“游戏是否可玩、可理解、可维护、可验证并能继续扩展内容”的角度审计整个游戏项目。

默认只审计并输出结论；只有用户明确要求整改时才修改项目。普通软件工程项目使用 `aki-project-audit`。

## 证据优先级

优先级从高到低：

1. 实际运行游戏并完成目标玩家路径；
2. 用户提供的录屏、截图、输入记录、运行日志和性能数据；
3. Scene、Resource、Asset、UI、输入、状态、存档和玩法代码；
4. 当前设计文档和其他项目事实源。

无法实际运行时，不得声称“已试玩”；必须明确区分实际观察与静态推断。

Godot 项目已安装且可使用 `gda` 时，优先用其运行时能力补充 scene tree、输入模拟、frame capture、日志、错误和性能证据；不能仅因 Skill 已安装就假设 CLI 可用。

涉及精简和架构收敛时，使用中央 `simplification.md` 与 `game-simplification.md`；游戏设计判断遵循中央 `game-development.md`，不在本 Skill 重复定义原则。

## 审计维度

按项目实际情况检查：

- **玩家路径与核心循环**：启动、理解目标、核心操作、失败 / 成功、结算、重试和继续游玩是否完整；
- **玩法状态与存档**：状态 Owner、修改入口、派生状态、存档恢复和跨场景状态是否一致；
- **Scene / Resource / Asset**：职责、生命周期、序列化引用、资源归属和删除 / 移动风险是否清晰；
- **数据与内容管线**：配置是否存在真实消费者，玩法数据、文案、本地化和表现资源是否与行为逻辑保持合理边界；
- **架构与复杂度**：是否存在重复状态、无消费者抽象、跨系统特判、过早兼容层或阻碍真实内容扩展的结构；
- **UI、反馈与可理解性**：玩家操作是否得到及时反馈，重要状态是否可读，界面是否与真实玩法状态一致；
- **测试与试玩**：自动测试是否覆盖确定性风险，当前版本是否经过真实玩家路径验证；
- **性能**：是否存在实际可观察的卡顿、加载、掉帧、内存或资源问题；
- **设计文档**：简版 / 详细设计和候选 / 计划 / 当前设计等信息状态是否与真实实现一致且只表达当前有效状态；
- **内容生产成本**：系统是否需要不成比例的关卡、美术、动画、音频、对话、事件或数值维护才能成立。

## 玩家路径

根据真实游戏选择路径，通常至少覆盖：

- 启动与首次进入；
- 菜单、设置和开始游戏；
- 第一次理解目标和输入；
- 核心玩法循环；
- 关键操作反馈；
- 失败、暂停、返回和恢复；
- 成功、结算、奖励或下一轮；
- 存档 / 读档存在时的恢复路径。

不机械覆盖无关路径。

## 工作流

1. 读取项目 `AGENTS.md`、当前设计文档、运行方式和目标玩家路径。
2. 能运行时从干净启动开始，以真实玩家流程建立运行证据。
3. 建立玩法系统、状态 Owner、Scene / Resource / Save 和内容管线的基本地图。
4. 对玩家问题继续读取相关代码和资源，区分表现症状与工程根因。
5. 对静态发现确认真实调用、玩家可达性和非代码引用，避免仅凭结构猜测。
6. 合并重复问题，优先保留高影响根因。
7. 给出最小整改方向和可复验的验收条件。

## 输出

每个重要发现包含：

- **路径 / 范围**：问题出现在哪条玩家路径或哪个系统；
- **证据类型**：实际观察 / 静态推断；
- **问题**：当前真实问题；
- **影响**：对玩家体验、正确性、维护或内容生产的影响；
- **建议**：最小整改方向；
- **验收**：修复后如何重新验证。

优先按 **阻断 / 高 / 中 / 优化机会** 排序；没有高置信问题时直接说明。

## 整改模式

用户明确要求整改时：

- 优先修复高影响、高置信问题，不顺手扩大范围；
- 工程修改执行对应自动测试和静态检查；
- 玩家路径受影响时必须重新实际运行并复验，自动测试不能替代试玩；
- 遵循项目 `AGENTS.md`、中央游戏开发原则和 Git 原则完成版本管理收尾。
