# aki-game-playtest-audit

## 目标

以玩家实际体验为中心回答：**游戏是否能被理解、操作、持续游玩，并在失败或异常后顺利恢复？**

本 Skill 审计的是玩家路径，不是代码风格。默认只输出问题和整改方向；用户明确要求后再修改项目。

## 证据优先级

优先级从高到低：

1. 实际运行游戏并完成目标玩家路径；
2. 用户提供的录屏、截图、输入记录和运行日志；
3. 场景、UI、输入、状态机和玩法代码；
4. 设计文档或描述。

如果无法实际运行，不得声称“已试玩”；必须把静态推断和实际观察分开。

## 玩家路径

根据项目真实结构选择路径，通常至少覆盖：

- 启动与首次进入；
- 菜单、设置和开始游戏；
- 第一次理解目标和输入；
- 核心玩法循环；
- 关键操作的视觉/声音/状态反馈；
- 受伤、失败、死亡或其他负面状态；
- 暂停、返回、重试、重新开始；
- 成功、结算、奖励或下一轮；
- 存档/读档存在时的恢复路径。

## 审计维度

- **可理解性**：玩家是否知道现在发生了什么、下一步做什么；
- **输入与反馈**：操作是否及时、有辨识度，失败输入是否有解释；
- **核心循环**：最重要的行为是否容易进入、重复和退出；
- **UI/信息层级**：重要信息是否可读，状态是否与游戏真实状态一致；
- **节奏**：等待、加载、教学、重复劳动和中断是否破坏体验；
- **失败恢复**：失败后能否明确、快速地继续；
- **状态一致性**：暂停、切场景、菜单、结算、存档等是否产生分裂状态；
- **玩家可感知价值**：复杂系统是否真的被玩家触发、理解和感知。

## 工作流

1. 读取游戏项目事实、输入方式和当前目标玩家路径。
2. 能运行时从干净启动开始，不跳过首次体验。
3. 对关键路径记录操作、预期、实际结果和阻断点。
4. 对问题读取相关场景、资源、UI 和代码，区分表现问题与系统根因。
5. 优先保留能稳定复现、明显影响体验的问题。
6. 给出最小修复方向和可复验的验收条件。

## 输出

每个重要问题包含：

- **Path**：玩家如何走到这里；
- **Observed / Inferred**：实际观察还是静态推断；
- **Problem**：玩家看到或感受到什么；
- **Impact**：阻断、困惑、误操作、节奏损失或感知不到价值；
- **Proposal**：最小整改方向；
- **Acceptance**：修复后怎样试玩确认。

优先按 Blocker / High / Medium 排序，不用大量主观偏好填充报告。

## 整改模式

用户要求修改时，遵循项目游戏开发原则和 Git 原则；修复后必须重新走受影响的玩家路径，代码测试不能替代实际试玩。

## 与 Superpowers 协作

本 Skill 独立可用。Superpowers 的 systematic debugging、TDD 和 verification 可以辅助定位与修复确定性问题，但不能替代真实玩家路径验证。
