# aki-project-audit

## 目标

从“项目是否正确、可维护、可验证、可继续演进”的角度审计普通软件工程项目，而不是只做代码风格检查或单次 diff review。

游戏项目使用 `aki-game-audit`。默认只审计并输出结论；只有用户明确要求整改时才修改项目。

## 事实来源

优先读取：

- 项目 `AGENTS.md`、README、架构 / 设计 / 接口文档；
- 构建、测试、运行、部署入口；
- 代码、配置、依赖、脚本和真实调用路径；
- Git 当前分支、工作区状态和与问题直接相关的历史；
- 能实际运行时的最小成功路径与失败路径。

涉及精简、删除复杂度或架构收敛时，使用中央 `simplification.md` 作为额外判断规则；不要在本 Skill 中重复定义精简原则。

## 审计维度

按项目实际情况检查：

- **正确性**：真实运行路径、边界条件、错误处理、资源释放、状态一致性；
- **架构与复杂度**：重复状态、无消费者抽象、生命周期分裂、无价值兼容层和可删除能力；
- **项目结构**：目录、模块、第三方依赖、生成内容和手写内容的职责边界是否清晰；
- **安全与配置**：凭据、敏感数据、危险默认值、环境差异、外部输入与权限边界；
- **测试与可靠性**：关键行为是否可验证，测试是否覆盖真实风险，是否存在静默失败；
- **可观测性**：关键失败和后台行为是否可定位；
- **文档与契约**：README、配置示例、接口说明和实现是否一致；
- **用户体验**：项目存在 UI 或交互路径时，检查状态反馈、错误 / 空状态、恢复路径和明显违反直觉的流程。

## 证据门槛

每个重要发现必须说明：

- **证据**：文件、符号、调用路径、配置、运行结果或可复现行为；
- **影响**：为什么它影响正确性、维护成本、风险或用户体验；
- **建议**：具体修复、删除、合并或验证什么；
- **置信度**：高 / 中 / 低；低置信猜测默认不进入主结论。

不为了数量堆积命名、格式或个人风格偏好等低价值问题。

## 工作流

1. 确认主要运行路径和本次审计范围。
2. 读取项目事实源，建立模块、状态、外部契约和用户路径的基本地图。
3. 先广泛扫描，再对候选读取真实调用点或运行证据。
4. 合并重复问题，优先保留根因而不是多个表面症状。
5. 对高影响候选补足复现方式、风险和验收条件。
6. 输出按优先级排序的审计结果，并明确已检查范围和未验证区域。

## 输出

优先输出少量高价值发现：

- **阻断**：会导致安全、数据、发布或核心功能风险；
- **高**：明显影响正确性、主要用户路径或长期维护成本；
- **中**：值得处理，但不阻断当前阶段；
- **优化机会**：有证据支持的进一步简化或体验提升。

如果未发现高置信问题，直接说明，不用低质量候选填满报告。

## 整改模式

用户明确要求整改时：

- 先处理高风险和高置信问题；
- 每个修改保持范围可解释、可验证；
- 遵循项目 `AGENTS.md`、中央开发原则和 Git 原则完成修改与版本管理收尾；
- 不把审计发现自动扩大成与当前整改目标无关的重构。
