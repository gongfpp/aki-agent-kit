# Git 版本管理原则

## 默认行为

- 位于 Git 仓库且任务会创建、修改或删除项目文件时，即视为 Git write task，应主动使用 Git 管理本次改动。
- 修改前先检查当前分支和工作区状态，识别并保护与本任务无关的已有改动。
- 除非用户明确要求“不要提交”“先留在工作区”或“先给我审查”，任务完成且验证通过后，应把本任务的逻辑完整改动提交为 commit；不要把“是否提交”作为例行确认问题。
- 只暂存和提交属于当前任务的改动，不顺带处理用户已有的无关修改。
- 是否 push、创建 PR 或执行其他远端操作，由当前项目 `AGENTS.md`、仓库既有流程、用户指令和 Agent 对任务边界的判断决定；本原则不设统一默认值。

## 分支与提交

- `main` 保持稳定，功能开发和较大修改优先在独立分支中进行；小而独立的改动可沿用当前仓库既有工作流。
- 一个独立需求或任务对应一个分支；同一需求的多轮迭代继续使用该分支，不按单次对话拆分。
- 每个逻辑完整、可独立理解的改动形成一个 commit，避免把无关修改混在一起。
- 在形成稳定阶段时及时 commit。
- 任务完成后检查改动与基本可用性，再按仓库现有流程决定是否 push、创建 PR、合并到 `main` 或继续保留本地分支。
- 合并完成后按仓库既有流程清理已完成分支。

## 安全边界

- 未经明确确认，不执行可能破坏历史或丢失代码的 Git 操作，如 `reset --hard`、`push --force`、rebase 后强制覆盖远端。
- Git 操作以保持历史清晰、方便回滚和避免代码丢失为原则；具体远端流程由 Agent 根据项目约束和当次任务判断。
