# Git 版本管理原则

## 默认行为

- 位于 Git 仓库且任务会创建、修改或删除项目文件时，即视为 Git write task，应主动使用 Git 管理本次改动。
- 修改前先检查当前分支、工作区和远端状态，识别并保护与本任务无关的已有改动。
- 除非用户明确要求“不要提交”“先留在工作区”或“先给我审查”，任务完成且验证通过后，应把本任务的逻辑完整改动提交为 commit；不要把“是否提交”作为例行确认问题。
- 仓库存在可用远端时，commit 后默认将当前任务分支安全地 push 到其 upstream；当前任务分支没有 upstream、但存在明确可用的 `origin` 时，可在首次 push 时建立 upstream。不要把“是否 push”作为例行确认问题。
- 用户明确要求只保留本地、没有可用远端/权限、仓库策略阻止 push，或 push 需要非快进、强制更新、历史重写时，不自动 push；明确报告原因，不自行绕过限制。
- 只暂存、提交和推送属于当前任务的改动，不顺带处理用户已有的无关修改。

## 分支与提交

- `main` 保持稳定，功能开发和较大修改优先在独立分支中进行；小而独立的改动可沿用当前仓库既有工作流。
- 一个独立需求或任务对应一个分支；同一需求的多轮迭代继续使用该分支，不按单次对话拆分。
- 每个逻辑完整、可独立理解的改动形成一个 commit，避免把无关修改混在一起。
- 在形成稳定阶段时及时 commit；存在远端时按默认行为同步当前任务分支。
- 任务完成后检查改动与基本可用性，再按仓库现有流程合并到 `main`；需要 PR 的仓库先 push 任务分支再创建或更新 PR。
- 合并完成后删除已完成的任务分支；远端允许且权限可用时同步清理对应远端分支。

## 安全边界

- 未经明确确认，不执行可能破坏历史或丢失代码的 Git 操作，如 `reset --hard`、`push --force`、rebase 后强制覆盖远端。
- 普通 fast-forward push、为新任务分支建立 upstream、创建/更新 PR 属于正常版本管理流程，不需要额外确认。
- Git 操作以保持历史清晰、方便回滚、远端可恢复和避免代码丢失为原则；具体拆分方式由 Agent 根据实际任务判断。
