# 独立游戏精简审计

本文件是 `simplification.md` 的游戏项目补充。先执行通用精简审计，再增加玩家路径、引擎资源和内容生产成本三个维度。

## 玩家路径是最高优先级证据

先实际运行游戏并确认当前可达流程、核心循环、失败/成功和结算路径，再判断系统是否有价值。

- 玩家真实路径无法触发的玩法、场景、按钮、事件、配置和资源优先进入候选；
- 只有 Debug、Demo、Prototype、Benchmark 或测试场景使用的系统必须明确开发价值；
- 代码层面优雅但玩家流程完全碰不到的能力仍然可能应该删除；
- 核心体验正在依赖的复杂度不能仅因结构不漂亮而删除。

## 不只搜索代码引用

游戏项目中的引用可能存在于脚本、Scene/Prefab、Resource、序列化数据、动画轨道、Input Map、Localization、Audio、Save Field、Group/Tag 和编辑器配置中。

删除前必须确认这些非代码引用，不能因为 `rg` 搜不到脚本调用就判断资源无用。

## 重点检查重复游戏状态

UI、Player、GameManager、关卡和存档容易各自保存同一个事实。审计时明确：

- 权威状态由谁拥有；
- 谁可以修改；
- 谁只观察；
- 存档保存和恢复什么；
- Signal、Timer、Coroutine 和 async task 的生命周期由谁结束。

同一游戏事实尽量只有一个运行时 Owner，UI 和存档不演化成第二套状态管理器。

## 审计未来承诺

多人、Mod、DLC、大世界、大量角色、跨引擎等未来能力只有在已经形成真实需求时才为它们承担当前复杂度。

当前项目规模明显小于抽象所服务的假想规模时，优先服务现有游戏。未来需求真正出现时再抽象，通常比现在猜未来便宜。

## 从内容成本反向审计功能

一项玩法的长期成本不仅是代码，还包括关卡、对话、美术、动画、音频、数值、事件和测试内容。

评估每个候选时问：这个系统需要多少持续内容生产才能不像半成品？如果内容成本明显高于玩家可感知价值，删除、合并或降级整个系统可能比优化实现更有效。

## 引擎与插件

引擎已经成熟提供的 Tween、资源加载、序列化、输入、导航、动画和生命周期能力，不应长期维护重复基础设施，除非存在明确特殊约束。

插件替换同样以净复杂度下降为标准；大量 Adapter、Override、兼容层和专属配置会抵消插件价值。

## 每个候选额外说明

除通用审计要求外，游戏候选还要明确：

- **Player impact**：玩家能否感知变化；
- **Content impact**：减少或新增多少持续内容生产；
- **Save/resource risk**：存档、场景、资源和序列化引用风险；
- **Tooling impact**：编辑器工具、Debug 流程和开发场景是否受影响。

功能删除后同时清理相关 Scene、Resource、Asset、Signal、Input Map、Config、Save Field、Localization、Animation、Audio、Test、Debug UI 和设计文档，避免留下半套失效系统。

最终目标是减少玩家无法感知的系统、重复状态、无价值内容生产、特殊分支、生命周期和开发者脑内负担，而不是单纯追求更少代码。
