# 独立游戏开发原则

本文件是在 `project-development.md` 基础上的游戏项目补充。判断标准优先服务于玩家实际体验和项目继续开发的成本，而不是架构形式本身；同时继承通用原则的适用边界，不要求已有项目为了匹配本文示例而重构。

## 玩家路径优先

- 修改前先理解当前真实玩家流程、核心循环、失败/成功、结算与重新开始路径。
- 判断系统价值时先确认玩家是否能够真实触发、感知和理解，再讨论代码形态。
- 操作反馈、状态反馈和核心循环完整性优先于外围系统和未来扩展能力。

## 先完成可玩的垂直切片

- 新玩法先形成最小可玩闭环，再扩大内容量和系统规模。
- 核心玩法尚未稳定时，不为多人、Mod、DLC、大世界或大规模角色等未发生需求提前建设架构。
- 抽象和数据化来自真实重复与变化压力，不来自想象中的未来规模。

## 原型转正式开发

- 原型阶段允许为了快速验证玩法采用临时结构；核心循环经真实试玩确认值得继续后，应主动检查这些结构是否还能承担后续开发，而不是默认继续叠加功能。
- 只优先稳定一旦改变会波及多个系统的高影响边界，例如运行时状态 Owner、主要修改入口、Scene / Node 生命周期、数据与行为职责、权威时间单位和 Save 边界。
- 检查结果可以是继续沿用当前结构；不要借此提前建设尚无真实需求的 Manager、Registry、EventBus、DI、ECS、Migration 或其他框架。

## 功能闭环

- 实现新的玩家功能前，至少明确：玩家如何真实触发、哪个权威状态发生变化以及由谁拥有和修改、玩家如何感知结果、如何从正常玩家路径判断功能完成。
- 这些问题无法回答时，先澄清玩法，不先建设 supporting architecture。
- 配置、状态、消费者和玩家反馈应尽量在同一个功能周期形成闭环；不要先增加没有真实消费者的字段、配置、接口或扩展点，再假设未来会用到。

## 数据驱动与内容解耦

- 游戏行为逻辑、可调整数据和玩家可见内容保持职责分离：代码负责规则执行、状态变化、数据结构和校验；数据负责参数与内容配置；文案负责玩家可见文本和本地化内容。
- 角色属性、武器参数、技能参数、掉落表、波次、经济数值、关卡参数等需要频繁调整或批量扩展的内容，优先使用引擎原生 Resource / Data Asset、配置表或项目已有数据机制，不把大量可调内容散落为行为代码中的 magic number。
- 对话、物品名称、技能说明、任务文本、UI 文案和剧情内容原则上不硬编码在行为逻辑中；需要本地化或批量维护时使用稳定 key / ID 和项目已有的 Localization / String Table 机制。
- 数据驱动服务于真实变化压力，不为少量稳定常量机械建立额外配置层；实现契约、算法常量和真正只属于代码的值可以保留在代码中。
- 数据、文案和代码的解耦是职责边界，不强制对应固定目录；具体文件位置和格式服从项目引擎、现有结构和项目级目录规范。
- 新增大量同类内容时，优先扩展数据而不是复制行为代码；修改数值或文案时应尽量避免触碰无关运行逻辑。

## 游戏目录与内容组织

- 具体目录树属于项目事实；优先遵循 Godot、Unity、Unreal 等引擎原生结构和当前项目已有约定，不为统一模板强行套用 `src/`、`assets/`、`scenes/` 等目录。
- 在引擎和项目允许时，游戏内容优先按功能、系统或实体聚合，让相关 Scene、Script、Resource、Asset、UI、Audio 和 Data 尽量靠近；只有确有共享或生产管线需求时才按文件类型集中拆分。
- 运行时资源与 Blender、Aseprite、PSD、DAW 工程等源素材分开管理，避免编辑源文件和游戏实际加载资产混为一体。
- 第三方插件、SDK、商店资源和外部内容与自有内容保持清晰边界，便于升级、删除、审计来源和许可证。
- Build、缓存、Import、Intermediate、Temp、Library、Derived Data 等可重新生成内容默认不作为长期源码管理；是否入库以引擎要求和项目真实发布流程为准。
- 项目结构随真实复杂度增长，不为“以后可能需要”提前创建大量空目录、Manager、系统层级或内容分类。
- Scene、Script、Resource、Asset、UI、Audio、Data、Save、生成物和导入产物的边界如果会影响未来放置位置，应在项目本地形成明确规则。
- 可从引擎和目录树直接推导的结构不重复写文档；只有非显然的资源归属、跨场景共享、生成/手写边界、命名与放置限制才需要长期记录。
- 简短放置约束可以进入项目 `AGENTS.md`；详细目录职责优先进入项目已有架构/GDD 文档，没有合适事实源时再使用 `docs/project-structure.md`。
- 调整目录前先检查场景序列化路径、Resource 引用、Import、Animation、Input、Localization、Save Schema 和编辑器配置，避免把文件移动当成普通文件系统重构。

## 游戏文档职责

游戏文档没有唯一行业标准目录、文件名或工具。重点是把不同状态和职责分开，让未来 Agent 能判断一段信息究竟是当前事实、已决定计划还是尚未确认的候选。

项目如果需要长期文档，通常需要区分这些语义：

- **当前设计事实**：已经确认的玩法、核心循环、规则和交互；可以由 GDD、Design 文档或项目已有事实源承载。
- **已决定的未来计划**：已经决定推进、但尚未全部进入当前实现范围的阶段、里程碑和功能；可以由 Roadmap、Milestone、Issue 等承载。
- **候选想法**：暂不实现、尚未确认的玩法、内容和灵感；可以由 Idea Backlog、Future Ideas、Issue 或其他候选池承载，不属于当前需求。
- **技术约束**：需要长期保持一致的架构、模块边界、状态、存档、资源、性能和平台约束；进入项目已有技术设计或架构事实源。
- **美术与内容规格**：美术风格、UI、动画、色彩、资产规格和其他长期视觉规则；进入项目已有美术或内容事实源。
- **需要追溯原因的重要决定**：只有难以逆转、具有真实取舍且未来需要知道“为什么”的决定才进入 ADR、decision log 或项目已有决策机制。

信息状态通常从“候选想法 → 已决定计划 → 当前设计/Scope → Implementation”逐步升级，但名称、载体和具体流程由项目决定。Agent 不得因为某个未来想法已经被记录，就自行把它升级成当前需求。

文档表达当前有效状态；玩法、架构或美术方向发生正式变化时直接更新对应事实源。避免把所有内容堆进单一巨型文档，也避免同一个事实在多个位置重复维护。

## 游戏状态与场景生命周期

- 同一运行时事实优先有一个清晰的权威来源，避免 Player、UI、GameManager、关卡和存档分别维护彼此可能漂移的副本；项目已经采用其他一致性模型时，以真实架构契约为准。
- UI 通常优先观察权威运行时状态而不是复制另一套状态；存档通常负责持久化和恢复，不应在没有明确架构理由时演化成并行运行时状态管理器。
- Scene、Resource、Asset、Signal、Timer、Coroutine 和 async task 都应能明确创建、连接、结束与释放责任；具体生命周期机制服从引擎和项目架构。
- 删除脚本或资源前同时检查序列化场景、动画轨道、Input Map、Localization、Audio、Save Field 和编辑器配置等非代码引用。

## 优先使用引擎能力

- Tween、资源加载、序列化、输入、动画、导航和场景生命周期等基础能力优先使用引擎成熟实现。
- 自建基础设施必须由真实约束驱动，不为了统一风格或未来可能换引擎。
- 插件只有在减少代码、兼容层、维护风险和内容生产成本的总和时才值得引入。

## 内容成本也是开发成本

- 玩法评估必须同时计算代码成本和持续内容生产成本。
- 需要长期制作大量专属关卡、对话、美术、动画、音频、数值或事件的系统，需要证明其玩家价值足以覆盖内容成本。
- 已经实现但需要巨大内容量才能不显得半成品的系统，可以降级、合并或删除。
- 优先复用内容生产管线，不为小功能建立长期独立工作流。

## 交互与可读性

- 玩家操作应获得及时、明确、可辨认的反馈，重要结果不能只存在于日志或内部数值中。
- UI 状态与游戏状态保持一致，避免界面与实际行为分裂。
- 输入、暂停、返回、失败重开和存档读取等基础路径保持可恢复并符合目标平台直觉。
- 美术表现服务于信息层级和玩法理解，不以视觉复杂度牺牲可读性。

## 存档、性能与试玩

- 修改 Save Schema、资源 ID、场景路径或关键枚举时明确旧存档兼容风险。
- 性能优化针对真实可感知的卡顿、加载、掉帧和内存问题，先定位瓶颈再引入对象池、缓存或异步机制。
- 自动化测试不能替代实际试玩；核心玩法改动至少验证真实玩家路径。
- 视觉、手感、节奏和可理解性主要通过实际运行、截图或录屏验证。
