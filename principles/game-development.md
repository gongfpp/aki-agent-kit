# 独立游戏开发原则

本文件是在 `project-development.md` 基础上的游戏项目补充。判断标准优先服务于玩家实际体验和项目继续开发的成本，而不是架构形式本身。

## 玩家路径优先

- 修改前先理解当前真实玩家流程、核心循环、失败/成功、结算与重新开始路径。
- 判断系统价值时先确认玩家是否能够真实触发、感知和理解，再讨论代码形态。
- 操作反馈、状态反馈和核心循环完整性优先于外围系统和未来扩展能力。

## 先完成可玩的垂直切片

- 新玩法先形成最小可玩闭环，再扩大内容量和系统规模。
- 核心玩法尚未稳定时，不为多人、Mod、DLC、大世界或大规模角色等未发生需求提前建设架构。
- 抽象和数据化来自真实重复与变化压力，不来自想象中的未来规模。

## 游戏目录与内容组织

- 具体目录树属于项目事实；优先遵循 Godot、Unity、Unreal 等引擎原生结构和当前项目已有约定，不为统一模板强行套用 `src/`、`assets/`、`scenes/` 等目录。
- 在引擎和项目允许时，游戏内容优先按功能、系统或实体聚合，让相关 Scene、Script、Resource、Asset、UI、Audio 和 Data 尽量靠近；只有确有共享或生产管线需求时才按文件类型集中拆分。
- 运行时资源与 Blender、Aseprite、PSD、DAW 工程等源素材分开管理，避免编辑源文件和游戏实际加载资产混为一体。
- 第三方插件、SDK、商店资源和外部内容与自有内容保持清晰边界，便于升级、删除、审计来源和许可证。
- Build、缓存、Import、Intermediate、Temp、Library、Derived Data 等可重新生成内容默认不作为长期源码管理；是否入库以引擎要求和项目真实发布流程为准。
- 项目结构随真实复杂度增长，不为“以后可能需要”提前创建大量空目录、Manager、系统层级或内容分类。
- Scene、Script、Resource、Asset、UI、Audio、Data、Save、生成物和导入产物的边界如果会影响未来放置位置，应在项目本地形成明确规则。
- 可从引擎和目录树直接推导的结构不重复写文档；只有非显然的资源归属、跨场景共享、生成/手写边界、命名与放置限制才需要长期记录。
- 简短放置约束可以进入项目 `AGENTS.md`；详细目录职责优先进入项目已有架构/GDD 文档，没有合适事实源时再使用 `docs/project-structure.md`。
- 调整目录前先检查场景序列化路径、Resource 引用、Import、Animation、Input、Localization、Save Schema 和编辑器配置，避免把文件移动当成普通文件系统重构。

## 游戏文档职责

游戏文档没有唯一行业标准目录，优先保持职责清晰、可搜索、持续更新，不为了模板完整度创建空文档。项目已有等价文档时沿用现有命名，不重复维护第二份事实。

常见职责可以按以下方式划分：

- **GDD / Design**：当前已经确认的玩法、核心循环、规则和交互，是“游戏现在是什么”的设计事实源。
- **ROADMAP**：已经决定推进但尚未全部进入当前开发范围的阶段、里程碑和未来功能，是“准备以后做什么”。
- **IDEA_BACKLOG / Future Ideas**：暂不实现、尚未确认的玩法、内容和灵感，是候选池，不属于当前需求；只有明确进入 Roadmap、GDD、Scope 或具体任务后才进入实现范围。
- **TECHNICAL_DESIGN / Architecture**：需要长期保持一致的技术架构、模块边界、状态、存档、资源、性能和平台约束。
- **ART_DIRECTION**：美术风格、UI、动画、色彩、资产规格和其他长期视觉规则。
- **decisions / ADR**：值得长期追溯“为什么这样决定”的重要设计或技术决策；普通小改动不创建记录。

设计信息的典型流转是：`灵感 → IDEA_BACKLOG → ROADMAP → GDD / Scope → Implementation`。灵感、已决定计划和当前需求必须保持区分，Agent 不得因为某个未来想法出现在文档中就自行实现。

文档表达当前有效状态；玩法、架构或美术方向发生正式变化时直接更新对应事实源。避免把所有内容堆进单一巨型 GDD，也避免同一个事实在多个文档重复维护。

## 游戏状态与场景生命周期

- Player、UI、GameManager、关卡和存档不得分别维护同一事实的独立真相。
- UI 观察权威状态；存档负责持久化和恢复，不应成为运行时第二状态管理器。
- Scene、Resource、Asset、Signal、Timer、Coroutine 和 async task 都要明确创建、连接、结束与释放责任。
- 删除脚本或资源前同时检查序列化场景、动画轨道、Input Map、Localization、Audio、Save Field 和编辑器配置等非代码引用。

## 优先使用引擎能力

- Tween、资源加载、序列化、输入、动画、导航和场景生命周期等基础能力优先使用引擎成熟实现。
- 自建基础设施必须由真实约束驱动，不为了统一风格或未来可能换引擎。
- 插件只有在减少代码、兼容层、维护风险和内容生产成本的总和时才值得引入。

## 内容成本也是开发成本

- 玩法评估必须同时计算代码成本和持续内容生产成本。
- 需要长期制作大量专属关卡、对话、美术、动画、音频、数值或事件的系统，需要证明其玩家价值足以覆盖内容成本。
- 已经实现但需要巨大内容量才能不显得半成品的系统，可以降级、合并或删除。
- 优先复用内容生产管线，不为小功能建立长期独立工作流。

## 交互与可读性

- 玩家操作应获得及时、明确、可辨认的反馈，重要结果不能只存在于日志或内部数值中。
- UI 状态与游戏状态保持一致，避免界面与实际行为分裂。
- 输入、暂停、返回、失败重开和存档读取等基础路径保持可恢复并符合目标平台直觉。
- 美术表现服务于信息层级和玩法理解，不以视觉复杂度牺牲可读性。

## 存档、性能与试玩

- 修改 Save Schema、资源 ID、场景路径或关键枚举时明确旧存档兼容风险。
- 性能优化针对真实可感知的卡顿、加载、掉帧和内存问题，先定位瓶颈再引入对象池、缓存或异步机制。
- 自动化测试不能替代实际试玩；核心玩法改动至少验证真实玩家路径。
- 视觉、手感、节奏和可理解性主要通过实际运行、截图或录屏验证。
