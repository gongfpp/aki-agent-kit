# 项目开发原则

本文件是个人开发偏好，不定义 `AGENTS.md` 标准本身。项目自己的代码、配置、接口契约、构建脚本和项目级文档始终优先于这里的通用建议。

## 适用边界

- 除安全、数据完整性和不可逆操作等需要硬边界的事项外，本文件提供的是跨项目默认判断规则，不是要求现有项目为了符合某种风格而重构。
- 项目已经存在合理、可验证且与当前目标兼容的架构或工作流时，保持项目自身契约；“与本原则写法不同”本身不构成修改理由。
- 原则优先描述目标、风险和判断标准，不指定具体框架、设计模式、目录树、库或实现方案；具体技术选择由项目事实和当前需求决定。
- 只有当现有实现造成真实正确性、维护、验证、安全或用户价值问题时，才把原则用于推动改动。

## 先确认事实

- 开始修改前确认仓库结构、构建入口、测试入口、相关文档和真实调用路径。
- 不根据目录名、技术栈经验或未来设想推断项目已经存在的行为。
- 能从代码和配置确认的信息不要反复询问；无法确认的事实不要编造。
- 对需要在多个会话反复读取的中央规则、规范或其他固定远程文档，优先使用已经建立的本地缓存；本地缓存存在时不要仅为确认 freshness 发起远程请求。只有缓存缺失、缓存明确失效或用户要求刷新时才访问远端；首次成功读取后应尽量保存到稳定本地路径，供后续会话复用。
- 先找到状态 Owner、资源 Owner 和外部契约，再决定修改位置。

## 写入意图与 Git 准备

- 一旦判断当前任务将创建、修改或删除项目文件，即视为已经形成 write intent；不要等到真正写文件时才处理 Git 前置规则。
- 位于 Git 仓库且当前会话尚未加载项目要求的 Git 原则时，应在做出具体修改承诺、制定实施性文件/分支计划或执行任何写入之前先完成读取；不能先答应修改、开始实施规划或动文件后再补读。
- 当前会话已经成功加载 Git 原则后继续遵循即可，不因后续轮次或同一任务重复读取；只有用户要求刷新、规则入口变化或明确需要重新核实时才重新读取。
- 纯分析、解释、审阅或只读调查如果没有形成文件写入意图，不因此触发 Git 写入流程。

## 意图与判断稳定性

- 用户询问“为什么没有做某事”、质疑当前选择或要求解释原因，不等同于授权执行该操作；先回答当前判断及其依据。
- 只有用户明确提出新的执行要求，或出现足以改变原判断的新事实、新约束时，才扩大任务范围或改变已经形成的执行决策。
- 已经基于项目事实和规则形成判断后，不因用户单纯追问、质疑、语气变化或期望 Agent 更积极而机械反转；先重新检查原判断是否仍成立，没有新依据时保持一致。
- 不为了显得主动、消除质疑或迎合用户而顺手执行额外修改、合并、发布、删除、远端操作或其他超出当前授权边界的动作。
- 用户提出的实现方式、操作建议或判断与项目目标或已验证事实冲突时，应说明依据并保持独立判断，而不是为了顺从而采用更差方案。

## 目录与项目结构

- 具体目录结构属于项目事实，不由本仓库提供一棵跨技术栈固定模板；优先遵循框架、语言、工具链和当前项目已经形成的约定。
- 新目录应对应稳定职责、边界或生产流程，不按单次需求、单个 Agent 会话或临时实现随意增加长期层级。
- 能直接从目录树看出的事实不额外写文档；只有非显然的放置规则、职责边界、生成/手写边界或未来很容易放错位置的约束才值得长期记录。
- 简短且会直接影响 Agent 放置文件的位置规则可以写入项目 `AGENTS.md`；详细目录职责优先进入项目已有架构文档，没有合适事实源且确有长期价值时可使用 `docs/project-structure.md`。
- 项目结构演进时直接更新当前权威说明，不在中央原则或项目文档中长期维护旧目录迁移历史。

## 围绕当前目标修改

- 优先完成能够直接满足当前需求的最小完整改动，避免顺手重构无关模块。
- 新行为优先复用已有扩展点、数据模型和生命周期。
- 抽象来自已经发生的变化和重复，不为尚未发生的需求预建通用框架。
- 用户提出的实现方式不适合目标时，说明原因并采用更符合目标的方案。

## 状态与生命周期

- 一个事实尽量只有一个权威状态来源；UI、缓存、持久化和派生状态不应各自演化成第二套真相。
- 资源、订阅、监听、线程、任务、Timer、连接和临时文件都应有明确 Owner 与释放时机。
- 多个 bool、sentinel、promise、token 或 cancellation flag 如果表达同一个事实，优先收敛为清晰的状态模型或生命周期对象。
- 注册产生副作用时必须有对应的清理机制。

## API、模块与依赖

- 模块边界服务于真实职责和变化频率，不为形式上的“解耦”增加无消费者的 Interface、Manager、Factory、Registry 或 Wrapper。
- 公共 API、配置、事件、序列化字段成为外部契约后，修改时明确兼容范围、迁移方式和失败行为。
- 标准库或成熟依赖只有在减少总维护成本时才值得引入；把同样复杂度搬进 Adapter 或 glue code 不算简化。
- 删除能力时同步清理相关测试、文档、配置、生成物和兼容分支。

## 错误与可观测性

- 失败应保留足够上下文用于定位，不吞异常，也不用成功返回掩盖失败。
- 凭据和环境差异显式管理，敏感信息不得进入仓库。
- 日志和诊断信息服务于真实故障定位，不为了可观测性再建立第二套状态系统。

## 测试与验证

- 测试强度与改动风险相称，优先覆盖真实行为路径、边界条件和容易回归的契约。
- 不为可逆、影响小、只是复述实现的改动机械增加测试。
- 先运行与本次改动直接相关的检查；这些通过后，只有出现新失败或未解决疑点时再扩大范围。
- 能运行项目时验证最小成功路径；不能运行时明确说明缺失环境，不伪造验证结果。

## 文档与生成物

- README、接口文档、配置示例和注释应与实际行为同步。
- 生成文件优先通过生成器更新；临时脚本、调试输出和一次性中间文件在任务完成前清理。
- 当前文档表达当前有效状态，废弃历史由 Git 保存，不通过不断追加说明维持。
