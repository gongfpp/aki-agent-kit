# 项目开发原则

本文件是个人开发偏好，不定义 `AGENTS.md` 标准本身。项目自己的代码、配置、接口契约、构建脚本和项目级文档始终优先于这里的通用建议。

## 先确认事实

- 开始修改前确认仓库结构、构建入口、测试入口、相关文档和真实调用路径。
- 不根据目录名、技术栈经验或未来设想推断项目已经存在的行为。
- 能从代码和配置确认的信息不要反复询问；无法确认的事实不要编造。
- 先找到状态 Owner、资源 Owner 和外部契约，再决定修改位置。

## 围绕当前目标修改

- 优先完成能够直接满足当前需求的最小完整改动，避免顺手重构无关模块。
- 新行为优先复用已有扩展点、数据模型和生命周期。
- 抽象来自已经发生的变化和重复，不为尚未发生的需求预建通用框架。
- 用户提出的实现方式不适合目标时，说明原因并采用更符合目标的方案。

## 状态与生命周期

- 一个事实尽量只有一个权威状态来源；UI、缓存、持久化和派生状态不应各自演化成第二套真相。
- 资源、订阅、监听、线程、任务、Timer、连接和临时文件都应有明确 Owner 与释放时机。
- 多个 bool、sentinel、promise、token 或 cancellation flag 如果表达同一个事实，优先收敛为清晰的状态模型或生命周期对象。
- 注册产生副作用时必须有对应的清理机制。

## API、模块与依赖

- 模块边界服务于真实职责和变化频率，不为形式上的“解耦”增加无消费者的 Interface、Manager、Factory、Registry 或 Wrapper。
- 公共 API、配置、事件、序列化字段成为外部契约后，修改时明确兼容范围、迁移方式和失败行为。
- 标准库或成熟依赖只有在减少总维护成本时才值得引入；把同样复杂度搬进 Adapter 或 glue code 不算简化。
- 删除能力时同步清理相关测试、文档、配置、生成物和兼容分支。

## 错误与可观测性

- 失败应保留足够上下文用于定位，不吞异常，也不用成功返回掩盖失败。
- 凭据和环境差异显式管理，敏感信息不得进入仓库。
- 日志和诊断信息服务于真实故障定位，不为了可观测性再建立第二套状态系统。

## 测试与验证

- 测试强度与改动风险相称，优先覆盖真实行为路径、边界条件和容易回归的契约。
- 不为可逆、影响小、只是复述实现的改动机械增加测试。
- 先运行与本次改动直接相关的检查；这些通过后，只有出现新失败或未解决疑点时再扩大范围。
- 能运行项目时验证最小成功路径；不能运行时明确说明缺失环境，不伪造验证结果。

## 文档与生成物

- README、接口文档、配置示例和注释应与实际行为同步。
- 生成文件优先通过生成器更新；临时脚本、调试输出和一次性中间文件在任务完成前清理。
- 当前文档表达当前有效状态，废弃历史由 Git 保存，不通过不断追加说明维持。
